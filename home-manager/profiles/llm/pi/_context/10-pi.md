# Using pi

Feature details live in pi's docs and the installed skills; read them when a
tool's own description does not settle the choice. This file carries only the
routing decisions.

Every capability is one tool call, and independent calls go in one message
instead of one call per step. Reach for the cheaper rung first and escalate only
when it cannot answer:

1. `read`, `grep`, `find`, `ls` — local, no process.
2. `symbol_search`, `module_report`, `read_symbol`, `read_enclosing` — pi-lens's
   local review index, no process.
3. `lens_diagnostics`, `lsp_navigation` — starts or reuses a language server.
4. `fetch_content` for a known static URL, PDF, video or GitHub repo;
   `get_search_content` for a stored `responseId` — one request, no synthesis.
5. `web_search` for finding URLs or open-web facts (2–4 varied queries in one
   call); `source_check` for verifying one claim with citations.
6. `mcp__<server>__<tool>` — an MCP tool that is not declared to you;
   `tool_search` declares it first, and reaching it starts the server.
7. `bg_run`, `subagent` — child process; a subagent also spends model tokens.
8. `interactive_shell` — a PTY behind a TUI overlay.
9. `browser_*` (pi-browser-use) — live DOM, login, JS rendering, clicks,
   screenshots, never a static page `fetch_content` can already read. Its
   `persistent` Chrome profile keeps logins; `browser_setup` signs in once.
10. `fusion_*` — five model slots per call.

## Delegation

- A shell command that outlives the turn → `bg_run`; anything you can wait for is
  `bash`.
- Read-only investigation that needs this conversation as context → `bg_delegate`.
- A role, edits, model tiering, or several children → `subagent`; `bg_delegate`
  when the child needs this conversation instead.
- A command that needs a TTY, or an interactive CLI (`vim`, `psql`, `ssh`, a
  REPL) → `interactive_shell`; its modes and spawn/attach recipes are in the
  `pi-interactive-shell` skill.
- Several model perspectives on one prompt → `fusion_reason` (reasoning only),
  `fusion_investigate` (a repo), `fusion_research` (the URLs you name), or
  `fusion_validate` (review of finished work).

None of these is worth it for what two or three direct calls finish: read the
file, run the command, answer.

## Code search and reading

- Identifier known, file unknown → `symbol_search`; file known, shape wanted →
  `module_report`; one symbol's body → `read_symbol`; the symbol around a line →
  `read_enclosing`; whole repo → `project_report`; `read` when nothing narrower
  fits. When the review graph is cold, `ast_grep_outline` gives syntax-only
  structure with no index.
- Exact string or regex → `grep`; structure matters (call shapes, imports,
  decorators) → `ast_grep_search` (`dump=true` to inspect the AST). One precise
  change → `edit`, a repeated structural rewrite → `ast_grep_replace`; references
  and renames → `lsp_navigation`, falling back to `grep` when no language server
  covers the file. Recipes: the pi-lens skills.

## Diagnostics and the done-check

- One file's type errors → `lens_diagnostics` with `source=lsp`; never `tsc` or
  `cargo check` through `bash`. When no language server covers the file, `bash`
  is the only option — and say so.
- Before declaring work done → `lens_diagnostics` `mode=all`, a cache read that
  also covers the non-LSP rules. `mode=full` is a project-wide sweep: not a
  per-file check, and not a substitute for a build or a test.

## MCP

- The servers' tools are hidden: run `tool_search` first, then use the exact names
  it declares. A codemode script waits for any server it names.
- Which server answers which request: versioned library or API documentation →
  `context7-mcp` (`resolve_library_id`, then `query_docs`); anything touching
  nixpkgs, NixOS, home-manager, flakes or Noogle → `mcp-nixos` (`nix`,
  `nix_versions`), not `nix search`; public code examples across GitHub →
  `grep-app` (`searchGitHub`); a PDF, Office file, image or URL to Markdown →
  `mineru-open-mcp` (`parse_documents`); the open web → `web_search`, not `exa`.
- Managing servers is `/mcp` in the TUI or `pi mcp list|add|remove|login|logout`;
  OAuth sign-in is manual (`pi mcp login <server>`).

## codemode: orchestration in one script

- Branching, a loop, fan-out, or filtering a large result down to what you need
  → one `codemode` script; its globals, the `models` API and the store are in
  its own description and the codemode docs.
- Two or three plain independent calls → make them directly in one message.
  codemode buys branching and context-saving and costs a sandbox round trip that
  hides each call's raw output; it loses exactly when you want to read the calls.

## Planning

- 3+ steps, a user-supplied task list, or multi-part instructions → `todo` (in
  memory, no tokens); `create_goal` only on an explicit user request.
- Never promote a todo list into a goal: goals are user-authorized, persistent and
  audited, todos are session scratch. With an active goal the tool surface is
  larger.
